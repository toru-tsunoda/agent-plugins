# 作業ダッシュボード

AI が自律的に作業する時に、人が進み具合を一目で見られるようにするダッシュボード。

- `.dev/dashboard.json`: タスクと質問。**AI が作業しながら書き換える**。
- `.dev/dashboard.html`: `build` で生成する表示用の HTML。手で編集しない。
- 指標（費用、キャッシュ読み込み率など）は Claude Code のセッションログから集計する。dashboard.json には書かない。

スクリプトは TypeScript で、Node.js 22.18 以降で動く（ビルドも依存パッケージも要らない。Python は不要）。このスキルのベースディレクトリの `scripts/` にある。コマンドはプロジェクトのルートで実行する。

| やること | コマンド |
|---|---|
| ダッシュボードを作る | `node <ベースディレクトリ>/scripts/dashboard.ts init` |
| HTML を作って開く | `node <ベースディレクトリ>/scripts/dashboard.ts build` のあと `open .dev/dashboard.html` |
| 常に最新で見る | `node <ベースディレクトリ>/scripts/dashboard.ts serve` をバックグラウンドで実行し、表示された URL を伝える |

`init` は `.dev/dashboard.json` と、同梱の料金表のコピー `.dev/prices.json` を作る。どちらも既存のファイルは上書きしない。`serve` は開くたびに集計し直し、30秒ごとに再読み込みする。ポートが使われていれば次の空いているポートを使う。

## 料金表を最新にする

費用は `.dev/prices.json` の単価で計算する。`init` でダッシュボードを作った直後は、必ず次の手順で料金表を最新にする（同梱のコピーは古いことがある）。`init` 済みのプロジェクトでも、`料金表` の日付（HTML の右上）が古い時や、`collect.ts` の出力の `unpriced_calls` が 0 でない時（単価のないモデルがある）は同じ手順をやる。

1. 最新の単価を調べる。**公式の料金ページ（https://platform.claude.com/docs/en/about-claude/pricing）を必ず WebFetch で取得する**。`claude-api` スキルのモデル価格表は補助に使う。スキルの表は古いことがあるので、これだけで済ませない。
   - 公式ページとスキルの表で単価が違う時は、公式ページを採る。
   - 公式ページが取得できない時は、スキルの表で代用してよい。その場合は `source` にスキルの表を使ったことを書き、最終報告で公式ページを確認できなかったと伝える。
2. `.dev/prices.json` の `models` を更新する。
   - `prefix` はログの `model` 名の接頭辞。`claude-opus-5` と `claude-opus-5-5` のように、長い接頭辞が短いほうより先に照合される。
   - 単価は USD / 100万トークン。`input`、`output`、`cache_read` を書く。`tier` は、Opus・Fable・Mythos 以上なら `high`、Sonnet・Haiku なら `low`（「運用状況」のモデルの警告に使う）。キャッシュ書き込みは `cache_write_multiplier`（5分は input の 1.25 倍、1時間は 2 倍）で計算するので、ここには書かない。
   - 新しいモデルは行を足し、なくなったモデルの行は古いログの集計のために残す。
3. `updated_at` を今日の日付にし、`source` に確認した場所（公式ページの URL など）を書く。
4. `build` で HTML を作り直し、右上の料金表の日付が変わったことを確かめる。

公式ページもスキルの表も調べられなかった時は、`prices.json` を書き換えない。同梱の単価のまま進めて、料金表が古いかもしれないことをユーザーに伝える。

## worktree ごとに分ける

PR のレビューや feature 開発を、フォルダ（git worktree）ごとに分けて見られる。

- 親リポジトリに `.dev/dashboard.json` がある状態で、worktree の中でセッションを始める（または `cd` / `EnterWorktree` で入る）と、フックがその worktree の `.dev/dashboard.json` と `.dev/prices.json` を自動で作る。手で `init` する必要はない。
  - 費用の上限と料金表は、親から引き継ぐ。タスクは空で始まるので、その worktree の作業に合わせてタスクを足す。
  - 親に `dashboard.json` が無いリポジトリや、git worktree でないフォルダでは何もしない。
- 親のダッシュボードは、`exclude_worktrees` が `true` なら worktree の分を数えない。二重に数えず、worktree ごとの費用が分かれる。
- `.dev/` は `.gitignore` に入れる想定なので、worktree のダッシュボードはコミットされない。
- worktree を消しても、ログが残っている間は親に合算されない（`.claude/worktrees/` 以下の場合。リポジトリの外に作った worktree は、もともと親に入らない）。

## dashboard.json の形式

```json
{
  "title": "foo 作業ダッシュボード",
  "project": "..",
  "created_at": "2026-09-30T01:00:00.000Z",
  "cost_cap_usd": 300,
  "session_cap_usd": 25,
  "exclude_worktrees": true,
  "gates": [{ "label": "sanity-review", "skills": ["sanity-review"] }],
  "tasks": [
    { "id": "T1", "status": "done", "title": "作業をタスクに分解する" },
    { "id": "T2", "status": "doing", "title": "ログイン画面の実装" },
    { "id": "T3", "status": "blocked", "title": "決済の組み込み", "blocker": "Q3 の回答待ち" },
    { "id": "T4", "status": "todo", "title": "E2E テスト" }
  ],
  "questions": [
    {
      "id": "Q3",
      "urgency": "高",
      "question": "決済は Stripe と PAY.JP のどちらにしますか？",
      "default": "Stripe で進める",
      "answer": null
    }
  ]
}
```

- `project`: 指標を集計するプロジェクトのパス。dashboard.json の場所からの相対パス。`null` なら全プロジェクト。
- `project`（続き）: フォルダ単位で集計する。作業ディレクトリがそのフォルダ自身か、その下にあるセッションが対象になる。
- `created_at`: ダッシュボードを作った時刻（ISO 8601）。`init` と worktree のフックが入れる。レビューゲートは、これより後のスキル実行だけを数える。無ければ時刻では絞らない。同じダッシュボードで新しい作業を始める時は、今の時刻に書き換えると、ゲートを数え直せる。
- `exclude_worktrees`: 既定は `true`（省略しても `true`）。`project` の中にある git worktree（Claude Code が作る `.claude/worktrees/` 以下を含む）のセッションを、この集計から除く。worktree の分は、その worktree 自身のダッシュボードで見る。`false` にすると、worktree の分も親に合算する。
- `gates`: レビューゲート。省略すると既定の3つ（下の「運用状況」を参照）。
- `tasks`: 1つのダッシュボードは1つの作業（PR のレビュー、feature の開発など）の範囲。作業を分けたい時は、フォルダ（git worktree）を分けてダッシュボードも分ける。タスクは全部画面に出る。
- `id`: タスクを区別できれば形式は自由（`T1`, `T2`, …）。
- `status`: `todo` / `doing` / `blocked` / `done` / `dropped` のどれか。`blocked` には `blocker` に理由を書く。`dropped` は「やらない」で、人が画面の「やめる」ボタンで付ける（AI が付けてもよい）。
- `urgency`: `高` / `中` / `低`。
- `default`: 回答が来なかった時に取る行動。
- `answer`: 未回答なら `null`。

## 更新のルール

- **タスクに着手した時**: `status` を `doing` にする。
- **タスクを終えた時**: `done` にする。
- **進めなくなった時**: `blocked` にして `blocker` に理由を書く。
- **ID と履歴**: ID は変えない。終わったタスクも消さない。
- **`dropped` のタスク**: 人がやらないと決めたタスク。**`status` を変えない。同じ内容のタスクを作り直さない。着手もしない**。関連する作業が要るように見えたら、`questions` で人に聞く。
- **人の判断が要る時**:
  - 既定の行動で進められるなら、`questions` に追加して、その既定の行動で作業を続ける。
  - 進められないなら、`urgency` を `高` にし、関係するタスクを `blocked` にする。
  - 質問の ID は `Q1`, `Q2`, … と通しで振る。
- **回答を受け取った時**: 回答はユーザーがチャットで返す。受け取ったら `answer` に書く。既定の行動と違う回答なら、その行動で進めた作業をやり直す。
- **書き換えた後**:
  - `node -e "JSON.parse(require('fs').readFileSync('.dev/dashboard.json'))"` で JSON として正しいか確かめる。
  - `build` で HTML を作り直す（`serve` で見ている時は不要）。

## 今の状態

ヘッダーの帯と、ブラウザのタブのタイトル（`[入力待ち（ターン終了）] …`）に、直近のセッションの今の状態を出す。人が今なにかすべきかを、色で分ける。

| 表示 | 色 | 意味 |
|---|---|---|
| 質問に回答待ち | 黄 | AskUserQuestion か MCP の入力フォームに、人の回答が要る |
| 権限の確認待ち | 黄 | 権限のダイアログに、人の許可が要る。**承認した後もツールが終わるまでこの表示のまま**（承認を知らせるフックが無い） |
| 入力待ち（ターン終了） | 青 | Claude がターンを終えた。結果を見て、次の指示を出す番 |
| 中断（入力待ち） | 青 | 人が中断した |
| 実行中 | 緑 | ツールを実行中。Bash・Agent・Skill・Web・MCP は 15 分で黄「実行中（長い）」、30 分で赤「実行中のまま応答なし」。Read・Edit などは 1 分で黄、5 分で赤 |
| 応答を生成中 | 緑 | ツールの結果か人の入力を受けて、次の応答を作っている。5 分で黄、15 分で赤「止まっている可能性」 |
| API エラーで停止 | 赤 | API エラーでターンが終わった |
| 終了 | 灰 | セッションを閉じた |

- 親がターンを終えた後もサブエージェントが動いていれば、「サブエージェント N 件が実行中」を添える。
- 帯の下の行に、セッション名（人が付けた名前か、自動で付いた名前）、ブランチ、ID の先頭 8 文字、実行中のツールを出す。
- ほかにも動いているセッションがあれば、その状態の件数を帯の最後に出す（「ほかのセッション 権限待ち 1 入力待ち 2」）。終わったセッションは数えない。

### セッション一覧

「運用状況」の下にある、開閉できる段（初期値は閉じている）。見出しの横に、状態ごとの件数が出る。

- 直近 24 時間に動いたセッション（最大 30 件）を、人の操作が要るもの（止まっている可能性・権限待ち・回答待ち → 入力待ち → 実行中 → 終了）から先に、同じなら新しい順に並べる。
- 各行に、状態、セッション名、ID、ブランチ、場所（`project` の中のサブディレクトリで動いた時）、その状態になってからの時間、実行中のツール、費用が出る。「◀ ヘッダー」が、ヘッダーの帯に出ているセッション。
- `exclude_worktrees` が `true` なら、`project` の中の worktree のセッションはこの一覧に出ない。worktree 一覧の「状態」の列に、各 worktree の直近のセッションの状態が出る。
- `claude -p` や SDK から動かしたセッション（ログの `entrypoint` が `sdk-` で始まる）は、ターンを終えたら「終了」にする。対話のセッションは、フックの記録が無いと閉じたことが分からないので、閉じた後も「入力待ち」のまま残る（24 時間で一覧から消える）。

### 判定のしかた

- **フックの記録を主にする。** このプラグインのフック（`hooks/record_state.ts`）が、プロンプトの送信、ツールの開始・終了、権限の確認、ターンの終了、サブエージェントの開始・終了、セッションの終了を、`~/.claude/glass-cockpit/sessions/<セッション ID>.jsonl` に1行ずつ足す（`CLAUDE_CONFIG_DIR` があればその下）。ダッシュボードの無いプロジェクトも含め、プラグインを読み込んだすべてのセッションで記録する（worktree 一覧や、全プロジェクトの集計でも使うため）。セッションログは非同期に書かれて遅れる（公式ドキュメントにもそう書かれている）ので、今の状態には向かない。
- **ログは補助にする。** ログの最後の記録がフックの最後の記録より新しければ、ログから判定する（人の中断など、フックが無い出来事）。
- **フックの記録が無いセッション**（プラグインを読み込む前から動いているセッションなど）は、ログから判定する。ターンの終了・中断・質問の回答待ちはログから確実に分かるので、そのまま出す。「実行中」と「応答を生成中」だけは推定になり、「?」や「ログから推定」が付く（ログだけでは、権限の確認待ちを「実行中」と区別できず、ログの書き込みの遅れもある）。
- 直近のセッションは、ログとフックの記録の新しいほうで選ぶ。**並行して動くセッションのうち、ヘッダーに出るのは最も新しい1つだけ**。それより前から止まっているセッションは、ヘッダーには出ない。
- フックの記録は、`cleanupPeriodDays` より古いものを、セッションの終了の時に消す。フックは何があっても Claude を止めず、何も出力しない。1回 40〜60 ミリ秒かかる。

## タスクの見え方と、人が消し込む方法

- 画面は、進行中（`doing`・`blocked`）と `todo` の先頭 10 件を表に出す。残りの `todo`、完了、やらないは折りたたむ。タスクが多くても、今やることが上に残る。
- 表の上の検索欄で、ID・状態・題・blocker を絞り込める。絞り込み中は、折りたたんだ中も開いて探す。
- **タスクの鮮度**: 「タスク」のタイルに、dashboard.json を最後に更新した時刻と、それが最後の動き（ログに書かれた最後の発言やツールの結果）より何分古いかが出る。1時間以上古いと黄になる。AI が動いた後に更新していないので、表のタスクが今の作業に追いついていないかもしれない。
  - 更新した時刻は、ファイルの更新時刻で見る。人が画面で「やめる」「戻す」を押した時も、更新に数える。
  - 最後の動きは、`project` の中のどのセッションでもよい。タスクと関係ない質問をしただけでも、古いと出ることがある。
- `serve` で開いた画面には、`todo`・`doing`・`blocked` の行に「やめる」ボタンが出る。押すと `status` が `dropped` になり、「やらない」に移る。「戻す」で `todo` に戻せる。完了したタスクはやめられない。
- `build` の HTML は静的なので、ボタンは出ない。消し込みたい時は `serve` で開くか、`dashboard.json` の `status` を `dropped` に書き換える。
- `serve` の書き込みは、同じPCの自分のブラウザからだけ受け付ける（別のサイトのページや別のホスト名からの要求は断る）。

## 指標の意味

ユーザーに聞かれたら、次の定義で説明する。集計する範囲は、`cleanupPeriodDays`（既定30日）の日数以内。Claude Code はこの日数より古いログを消す。

- **費用（API 換算）**: トークン数 × API 単価（`.dev/prices.json`）の概算か、Claude Code がセッションに記録する費用（cost-state）の大きいほう。定額プランでも API 単価で出す。
- **直近のセッション**: 最後に動いたセッションの費用。
- **キャッシュ読み込み率**: 入力トークンのうち、プロンプトキャッシュから読めた割合（トークン量で加重）。
- **ツールのエラー率**: エラーで返ったツール呼び出しの割合。拒否されたものは含めない。終了コードが 0 以外の Bash（grep で見つからなかった時など）も、ツールの失敗ではなくコマンドの結果なので含めず、件数をタイルに別に出す。
- **文脈の読み落とし**: 直前の呼び出しの文脈の半分も、キャッシュから読めなかった回数のうち、想定外のもの。システムプロンプトやツールの一覧が途中で変わった時などに起きる。
  - 想定内の次の3つは数えず、タイルに内訳を出す。キャッシュ切れ（前の呼び出しから、キャッシュの寿命より長く空いた。寿命は5分で、1時間のキャッシュを書いたセッションは1時間）、モデル変更、縮小（compact などで、文脈が前の半分未満になった）。
  - 色は、直近のセッションで想定外の読み落としがあった時だけ付ける（黄）。
- **自動続行**: 人以外（タスクの完了通知、別のエージェントからのメッセージ）がきっかけで始まったターンの数。
- **拒否**: 人・権限ルール・ハーネスが止めたツール呼び出しの数（承認されなかったコマンド、作業ディレクトリの外の読み込みの禁止、worktree の外に出るコマンドなどを含む）。
- **API エラー**: API 呼び出しが失敗した数。

### 運用状況

画面の「運用状況」の段。どれもセッションログのツール呼び出しから数える。

見出しで開閉できる。初期値は閉じていて、閉じていても見出しの横に要約が出る（サブエージェント・Codex の回数、異常があれば色付き）。今の状態は、この段ではなくヘッダーに出る（下の「今の状態」）。開いた状態は、ブラウザのタブを閉じるまで覚えている。

- **最後のツール**: 直近のセッションで最後に呼んだツールと、その時刻。
- **人を待った時間**: AskUserQuestion を出してから、答えが返るまでの時間の合計と最長。
- **サブエージェント**: Agent ツールの呼び出し回数、種別ごとの内訳、`subagents/*.jsonl` の分の費用と全体に占める割合（トークン数 × 単価の概算）。いま動いているサブエージェントの数は、ヘッダーの「今の状態」に出る。
- **Codex の実行**: Bash で `codex exec` を実行した回数、失敗（エラーで返った数）、最長の実行時間。`command -v codex` のような確認は数えない。
- **モデル**: 直近のセッションで、メインのエージェントが最後に使ったモデル。これが Opus 未満（Sonnet・Haiku）なら黄で警告し、閉じた見出しの横にも出す。期間内の Opus 未満の呼び出し回数は、メインとサブエージェントに分けて出す（色は付けない）。格は `prices.json` の各行の `tier`（`high` は Opus 以上、`low` はそれ未満）で決まる。`tier` が無い行は名前から推す（`opus`・`fable`・`mythos` は `high`、`sonnet`・`haiku` は `low`）。
  - Explore などのサブエージェントが Haiku を使うのは普通なので、サブエージェントの分では警告しない。前のセッションの分でも警告しない（今の作業には関係ないため）。
- **レビューゲート**: 作業が進む前に通したい手順を、スキルの実行で確かめる。`Skill` ツールで呼ばれたスキルと、`/スキル名` で起動したスキルの両方を数える。プラグイン名の違いは無視する（`codex-consultation:codex-consultation` も `codex-consultation`）。
  - 数えるのは、今の作業の分だけ。前の作業の実行で、ゲートが通ったように見えないようにする。
    - **今のブランチ**で実行したもの（ログの `gitBranch` で見る）。ブランチの分からない実行（detached HEAD の時や、git 管理にする前の実行）は数えない。`project` が detached HEAD の時と、git のリポジトリでない時は、ブランチでは絞らない。
    - **ダッシュボードを作った後**（`created_at` 以降）に実行したもの。
    - 絞った範囲は、タイルの見出しに出る（「ブランチ feature-x · 09/30 10:00 以降」）。
  - 既定は、Codex/subagent に相談（`codex-consultation` か `subagent-consultation`）、対話コンテキスト export（`conversation-context-export`）、`sanity-review`。
  - 差し替えるには、`dashboard.json` に `"gates": [{ "label": "表示名", "skills": ["スキル名", ...] }]` を書く。いずれかのスキルが1回でも実行されていれば通ったことになる。

### worktree 一覧

「運用状況」の下にある、開閉できる段。初期値は閉じていて、見出しの横に件数・合計費用・進行中のタスク数・未回答の質問数が出る。

- 今開いているリポジトリの git worktree（`git worktree list`）を、メインを先頭に、あとは最近動いた順に並べる。各行に、ブランチ、場所、状態（その worktree の直近のセッション）、費用、セッション数、最後の動き、タスク（完了 / 全体、`doing` の数。dashboard.json が最後の動きより1時間以上古ければ、その時間）、未回答の質問が出る。
  - 「◀ この画面」が、今見ているダッシュボードの worktree。
  - 費用は、その worktree の中で動いたセッションだけ。中にある別の worktree の分は含めない。だから行の費用を足すと、二重にならず合計になる。
  - タスクと質問は、その worktree の `.dev/dashboard.json` から読む。無ければ「ダッシュボードなし」。ディレクトリが無くなっていて `git worktree prune` の対象なら「ディレクトリなし」。
- worktree が1つだけの時と、git のリポジトリでない時は、この段を出さない。
- `project` を `null` にした（全プロジェクトを集計する）ダッシュボードには出さない。
- 各 worktree のログを別々に集計するので、worktree が多いと `serve` の再読み込みが遅くなる。
- セッションは、最初に動いた作業ディレクトリの worktree に数える。途中で `EnterWorktree` などで移った分は、最初の worktree に数えられる。
